KV cache

When generating token \(t\), the keys and values for tokens \(1\dots t-1\) don't change, so cache them and compute only the new token's \(\mathbf q,\mathbf k,\mathbf v\). Each step costs \(O(t)\) instead of \(O(t^2)\). The cache is large:

$$\text{KV memory}=2\times n_{\text{layers}}\times n_{\text{kv heads}}\times d_{\text{head}}\times\text{seq len}\times\text{batch}\times\text{bytes}$$

Example: 32 layers, 32 KV heads of 128 dims, fp16, 8k context: \(2\cdot32\cdot32\cdot128\cdot8192\cdot2\) bytes ≈ 4.3 GB per sequence. Grouped-query attention (several query heads share one KV head; e.g. 8 KV heads) cuts this 4×. Multi-query attention uses a single KV head.

Other techniques

  • FlashAttention: computes exact attention in tiles that fit in fast on-chip memory, using an online softmax, never materializing the \(n\times n\) matrix in GPU main memory. Much faster and memory-linear.
  • Continuous batching + paged KV cache (vLLM): add and remove requests from the batch at each step; store the cache in pages like virtual memory to avoid fragmentation.
  • Speculative decoding: a small draft model proposes several tokens; the large model verifies them all in one pass and accepts a prefix. The output distribution is unchanged, latency drops.
  • Mixture of experts: replace the FFN with \(E\) expert FFNs and a router; each token uses the top-\(k\): \(\mathbf y=\sum_{i\in\text{top-}k}g_i(\mathbf x)E_i(\mathbf x)\). Total parameters grow while compute per token stays small. Needs a load-balancing loss so experts are used evenly.
  • Long context: RoPE scaling, sliding-window or sparse attention, and state-space / linear-attention hybrids.
Prefill vs decode

Processing the prompt (prefill) is compute-bound and parallel. Generating tokens (decode) is memory-bound: each new token must read all the weights and the KV cache from memory. That's why output tokens cost more than input tokens, and why quantization and batching help decode so much.
