Why learning for robots is hard

Text and images are abundant on the internet; robot experience is not. Every data point costs real time on real hardware, mistakes can break things, and the world varies endlessly (lighting, friction, object shapes). The main strategies attack this data problem from different directions.

Imitation learning

Its weakness is covariate shift: a small error takes the robot to states the expert never visited, where the policy is worse, so errors compound (roughly quadratically in the horizon). Fixes:

  • DAgger: run the learned policy, ask the expert what they would have done in the states it actually reaches, add those labels, retrain.
  • Action chunking: predict a short sequence of future actions instead of one, which reduces compounding and handles pauses in demonstrations.
  • Expressive action distributions: human demos are multi-modal (go left or right around an obstacle). Averaging modes with MSE produces the invalid middle. Diffusion policies and discretized action tokens model multiple modes (Diffusion Models).

Sim-to-real transfer

Simulators (MuJoCo, Isaac, PyBullet, Gazebo) generate unlimited, safe experience, but they never match reality exactly. Techniques to bridge the gap:

  • Domain randomization: randomize masses, friction, motor strength, latency, textures and lighting during training, so reality looks like just another variation.
  • System identification: measure real parameters and calibrate the simulator.
  • Privileged teacher, deployable student: train a teacher policy with access to simulator-only information (exact terrain, contact forces), then distil it into a student that only uses real sensors.
  • Fine-tuning on real data with a small amount of real-world interaction.

Learned quadruped and humanoid locomotion controllers trained this way now handle stairs and rough terrain that hand-designed controllers struggled with.

Foundation models for robotics

  • LLMs as planners: a language model breaks "clean up the table" into steps and calls skills (pick, place, open), checked against what the robot can actually do. This is tool use (Agents & Tool Use) where the tools move physical objects.
  • Vision-language models for perception: open-vocabulary detection and segmentation let a robot find "the red mug" without a dedicated detector (Vision Transformers, CLIP & Self-Supervised Vision).
  • Vision-language-action (VLA) models: start from a pretrained vision-language model and fine-tune it to output robot actions (as discrete tokens or through a continuous action head) given camera images and an instruction. Trained on large multi-robot datasets, they generalize better to new objects and instructions than single-task policies.
  • World models: learned simulators that predict future observations from actions, used for planning or for generating training experience.
Safety is not optionalPhysical robots can injure people. Production systems keep learned policies inside safety envelopes: velocity and force limits, emergency stops, collision checking by classical planners, and human oversight during deployment.

The modern recipe for a manipulation skill

  1. Collect 50–500 teleoperated demonstrations of the task, with varied object positions.
  2. Train a policy that maps camera images (and joint states) to action chunks, using a pretrained vision encoder.
  3. Evaluate on held-out object placements; measure success rate over many trials, not one video.
  4. Collect corrective data where it fails (DAgger-style), retrain, repeat.
  5. Optionally fine-tune with RL in simulation or in the real world for robustness.
import torch, torch.nn as nn

class BCPolicy(nn.Module):
    """Behaviour cloning: image features + joint state -> a chunk of k future actions."""
    def __init__(self, vision_dim=512, state_dim=7, action_dim=7, chunk=8):
        super().__init__()
        self.chunk, self.action_dim = chunk, action_dim
        self.net = nn.Sequential(nn.Linear(vision_dim + state_dim, 512), nn.GELU(),
                                 nn.Linear(512, 512), nn.GELU(),
                                 nn.Linear(512, chunk * action_dim))
    def forward(self, vision_feat, state):
        out = self.net(torch.cat([vision_feat, state], dim=-1))
        return out.view(-1, self.chunk, self.action_dim)

policy = BCPolicy()
feats, state = torch.randn(32, 512), torch.randn(32, 7)        # from a frozen image encoder
target = torch.randn(32, 8, 7)                                  # demonstrated action chunks
loss = nn.functional.mse_loss(policy(feats, state), target)     # unimodal; use diffusion heads for multimodal demos
Practice problems
  1. A behaviour-cloned policy works for the first seconds of a task, then drifts and fails. What is happening and what would you try?
    Solution
    Covariate shift: small errors lead to unfamiliar states where the policy is worse, so errors compound. Try DAgger-style corrective data, action chunking, more varied demonstrations, and a policy class that models multi-modal actions.
  2. Why randomize friction and motor strength in simulation?
    Solution
    So the policy cannot overfit to one exact simulator. If it works across a wide range of physics, the real robot is likely to fall inside that range.
