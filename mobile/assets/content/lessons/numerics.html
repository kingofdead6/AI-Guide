Why bf16 won

bf16 keeps fp32's 8 exponent bits, so it has the same range: gradients rarely overflow or underflow. It gives up precision instead, which neural networks tolerate well. fp16 has more precision but a tiny range, so small gradients underflow to zero unless you multiply the loss by a large scale factor before backprop and divide afterwards (loss scaling).

Classic failure modes

  • Overflow: e100e^{100}e100 is infinite in fp32; e12e^{12}e12 already overflows fp16.
  • Underflow: a product of many probabilities becomes exactly 0. Work in log space.
  • Catastrophic cancellation: subtracting nearly equal numbers loses most significant digits, e.g. computing variance as E[X2]−E[X]2\mathbb E[X^2]-\mathbb E[X]^2E[X2]−E[X]2 on large values.
  • Swamping: adding a tiny number to a huge one does nothing (1+10−8=11+10^{-8}=11+10−8=1 in fp32). This is why sums and matmul accumulations are done in fp32 even when inputs are bf16.

def stable_sigmoid(x):
    return np.where(x >= 0, 1 / (1 + np.exp(-x)), np.exp(x) / (1 + np.exp(x)))

def logsumexp(z):
    m = z.max(); return m + np.log(np.exp(z - m).sum())
print(logsumexp(np.array([1000.0, 1000.0])))                # 1000.693..., naive version gives inf
Practice problems
  1. Your fp16 training run shows loss = NaN after a few hundred steps. List three likely causes and fixes.
    Solution
    (1) Overflow in activations or logits: switch to bf16 or clamp/normalize. (2) Gradient underflow then a division by zero: enable dynamic loss scaling (torch.amp.GradScaler). (3) An unstable operation such as log(softmax(x)) or log(0): use fused, stable functions like F.cross_entropy on logits. Also lower the learning rate and add gradient clipping.
  2. Why accumulate a bf16 matrix multiplication in fp32?
    Solution
    A dot product of length 4096 adds thousands of terms. With only 8 bits of mantissa, once the running sum is large, each new small term is mostly rounded away (swamping). Accumulating in fp32 keeps the sum accurate, then the result is rounded once.
